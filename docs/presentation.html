SRE interview walkthrough

Quiet on-call, full disk

Two weeks in. No pages, a green dashboard, and a Prometheus that fills its disk at night and gets OOM-killed twice a week. Then five teams ask for their own Prometheus and management asks for one dashboard.

Stack: kind, Prometheus Operator v0.72, Grafana 10.4 Task 1: find and fix the monitoring stack Task 2: tenant automation and federated queries
Task 1

What the dashboard hid

The "Request Rate" panels were flat at zero. That read as healthy. The service was doing about 30 requests per second the whole time.

Dashboard request rate 0 sum(rate(service_request_total[5m]))
Real request rate ~30 req/s 5 threads, 150 ms sleep each
Alerts that could page 0 ruleSelector set, no PrometheusRule, no Alertmanager

Every series was created with value 1 and never incremented again, so rate() of each was zero and the sum of zeros was zero. The panel was not wrong, it was measuring the wrong shape of data. The "quiet on-call" was silence, not health.

Task 1

Root cause: one label

request_total = Counter(
    "service_request_total",
    "Total requests processed",
    ["service", "team", "request_id"],   # a fresh UUID per request
)

A per-request identifier as a metric label means one new time series per request, forever. The client library never expires label children, Prometheus keeps every series in the head block, and memory and disk scale with series count.

Measured on the kind cluster. Growth is linear with traffic and never plateaus.

The only label with unbounded values. A real service at 1 000 req/s would create 3.6 million series an hour.

Task 1

Why disk and memory, not just slow queries

  1. Head block holds every active series in memory. 1Gi container limit, RSS grows with series, kernel kills it.
  2. Storage was an emptyDir. No storage block on the Prometheus CR, so the TSDB lived on the node's container filesystem. That is the disk that filled. Every restart lost all data.
  3. retentionSize did not protect the disk. It only counts persisted blocks. The WAL and the head chunks, the last two to three hours, are not counted, and with millions of series they alone exceed 1GB.
  4. No guard rails on the scrape path. No sample limit, no label limit, no scrape timeout. Prometheus accepted a 900 KB, ever-growing payload every 15 seconds.
  5. No self-monitoring. Prometheus did not scrape itself. Head series, WAL size and RSS were invisible.
Task 1

The fix, in layers

Remove the cause, then make sure the same class of bug cannot take the server down again, then make it visible.

app/app.py
Drop request_id. Labels are service and team only, 15 series. Add a bounded latency histogram. Add a TEAM env var for task 2.
Prometheus CR
enforcedSampleLimit: 5000, label count and length limits. A bad exporter now fails its scrape and shows up == 0 instead of filling the TSDB. 5Gi PVC, retention: 24h, retentionSize: 3GB leaves WAL headroom.
ServiceMonitors
scrapeTimeout: 10s, honorLabels: true. New prometheus-self monitor so the server observes itself.
Alerting
Alertmanager deployed and wired. Rules: TargetDown, ScrapeSampleLimitExceeded, PrometheusSeriesGrowthAbnormal, PrometheusStorageNearlyFull, ServiceRequestRateZero, ServiceMetricCardinalityHigh (fires above 100 series).
Dashboard
New "Prometheus health" row: head series, series created per second, blocks and WAL on disk, scrape duration, RSS. The panels that would have shown this on day one.
CRDs
AlertmanagerConfig and ThanosRuler CRDs were missing. The operator's Alertmanager controller silently refused to reconcile without the first one.

Tenant isolation

Everything a team owns lives in team-<name> and carries tenant: <name>. The Prometheus CR selects ServiceMonitors, PodMonitors and rules only from namespaces and objects with that label, and its ServiceAccount has a namespace-scoped Role, not a ClusterRole.

Task 2

The federation contract

Raw series never leave a tenant. The central server only accepts series whose name follows the recording-rule convention level:metric:aggregation.

# k8s/prometheus-operator/federation.yaml, one ServiceMonitor for all tenants
namespaceSelector: { any: true }
selector: { matchLabels: { monitoring.sre/federate: "true" } }
endpoints:
  - port: web
    path: /federate
    honorLabels: true
    params:
      "match[]":
        - '{__name__=~"[a-z_]+:[a-z_]+:[a-z0-9_]+"}'
        - '{__name__="up"}'

Why this shape

Discovery is by label across all namespaces, so a new tenant is a federation target within one scrape interval with zero central change.

Tenants decide what they publish by writing recording rules. They cannot flood the central server, so the task 1 incident cannot propagate upward. Measured: 2 to 10 samples per federation scrape per tenant.

Contract today

team:service_request:rate5mrequest rate dashboard
team_service:service_request:rate5mper service
team_service:service_request_duration_seconds:p95_5mlatency
team:prometheus_tsdb_head_series:sumseries budget alert

Central alerts on top: TenantFederationDown, TenantFederationStale, TenantSeriesBudgetHigh above 50 000 series. The platform team hears about a broken or overloaded tenant before the tenant does.

Task 2

Adding a tenant

A tenant is a directory in git rendered from one template. Onboarding is a pull request.

scripts/add-tenant.sh foxtrot            # render k8s/tenants/foxtrot/, open a PR
scripts/add-tenant.sh foxtrot --apply    # same, and apply to the current cluster

CIValidatekustomize build, kubeconform against operator CRDs, policy check that limits and storage are set
platformReview and mergeThe only human gate. Budget changes are visible in the diff
Argo CDSyncApplicationSet directory generator over k8s/tenants/*
operatorReconcileStatefulSet, config, PVC for the tenant Prometheus
centralDiscoverService with monitoring.sre/federate=true appears, /federate scrape starts
grafanaDatasource appearsSidecar sees the labelled ConfigMap, writes it, reloads provisioning
doneOn the global dashboardMeasured: about 90 seconds from --apply to federated target up

Removing a tenant is git rm -r k8s/tenants/foxtrot and a sync. Argo CD prunes the namespace and the PVC goes with it.

Task 2

Where this stops, and what comes next

Federation is a snapshot

Resolution is the federation interval and there is no drill-down into raw tenant data from the centre. When management wants ad-hoc queries: Thanos Query fanning out to a sidecar next to each tenant, or Grafana Mimir with one tenant ID per team. Both keep one global query endpoint and add object-storage retention, which removes "Prometheus ran out of disk" as a failure mode for good. The tenant directory structure does not change, the Prometheus CR gains a thanos: or remoteWrite: block.

Central Prometheus is a single point of failure

For the management view only, tenants keep working without it. replicas: 2 on the central CR is the cheap fix.

Grafana and Alertmanager are shared

Folders plus teams plus non-editable datasources on OSS Grafana. Per-tenant AlertmanagerConfig gives teams their own routes; an Alertmanager per tenant fits the same template if noisy neighbours appear.
